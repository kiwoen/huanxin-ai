# 系统架构与底座评估

## 推荐的逻辑边界

手机/平板/扫码器负责现场交互；仓储网页负责扫码、显示和确认；库存业务 API 负责权限、校验、防重和审批；关系数据库保存商品、货位、库存动作和用户；AI 辅助服务通过受控接口提供资料提取、只读查询和位置建议。

**库存 API 和数据库是库存事实来源。** AI 只能通过受控接口读取或提交待确认草稿，不持有可任意写库的权限。

## 库存账设计要点

- 将每次收货、发货、移库、盘点调整记为独立业务动作。
- 当前余额可以为查询性能做汇总，但需可由动作流水核对或重建。
- 同一请求用唯一标识防止网络重试导致重复入账。
- 库存写操作在事务中完成；动作与余额更新必须一起成功或一起回滚。
- 已确认动作不可无痕删除；错误通过冲销/更正记录修复。

## 底座候选

| 候选 | 适配场景 | 资料显示的能力 | 评估时要确认 |
|---|---|---|---|
| InvenTree | 零件、配件、电子元件和层级货位管理 | 库存项关联数量、货位、批次/序列号；记录库存追踪；支持扫码移库、盘点和位置扫描 | 是否覆盖订单履约、单位换算和行业流程；权限、导入、报表和许可证边界 |
| ERPNext | 仓储还需和采购、销售、库存估值或其他 ERP 流程衔接 | 官方文档含收货、发料、仓间转移、Pick List 扫码等能力 | 对简单仓储可能偏重；实施、学习、升级及许可证义务 |
| Odoo Inventory/Barcode | 需要较完整采购、销售、收货、发货业务流程 | 官方文档介绍扫码器或手机收发货、商品与货位扫描 | 按目标版本、部署方式核对功能范围、授权和维护成本 |
| 自建轻量系统 | 流程差异明确且现有系统无法合理配置 | 可按现场流程定制 | 需自行承担库存一致性、权限、备份、升级和长期维护 |

这不是最终选型结论。建议在同一份测试商品表上各走一次“收货—上架—移库—出库—盘点”，以操作时间和缺口清单作比较。官方能力链接见 [网络资料与依据](references.md)。

## 设备与网络

- 先试用现有 Android 手机/平板摄像头扫码，或键盘模拟型蓝牙/USB 扫码器。
- 少量货位标签可用普通标签打印方式验证；确定标签材质、尺寸和耐久度后再采购热敏打印机。
- 若现场网络不稳，先记录断网频率和影响；离线队列需要冲突解决、重复操作保护和同步审计，不应被当成“加一个缓存”。
- 先不采购 RFID、机械臂、输送线等高成本设备，除非吞吐量和测算已经证明其必要性。

## 与幻炘 AI 的适配

- 通过明确的库存 API/工具接入幻炘 AI，优先做商品草稿提取、只读查询和位置推荐。
- 写入操作调用受限命令，例如建立待审核收货草稿；正式入账由员工扫码和确认。
- 每个 AI 动作携带用户、来源、输入摘要和结果审计；敏感单据按客户授权处理。
- 如果仓储系统已有合适的库存模块，幻炘 AI 作为可插拔助手，不替代其库存账本。
